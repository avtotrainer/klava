# KLAVA — განვითარების და შემოწმების პროცესი

## Source of truth

- **GitHub:** კოდი, ტექნიკური დოკუმენტაცია, Product Specification, Issues, PR, CI.
- **Google Drive:** სასწავლო მასალები და არაკოდური რესურსები.
- **Slack:** განხილვები და საჭირო შეტყობინებები.
- **ChatGPT Project:** AI-ის ოპერაციული წესები; ატვირთული ასლები ავტომატურად განახლებულად არ ჩაითვალოს.

## ყოველდღიური ცვლილება

1. **Understand:** ჩამოაყალიბე მოთხოვნა და მოსალოდნელი ქცევა.
2. **Inspect:** წაიკითხე კოდი, არსებული ტესტები, სპეციფიკაცია.
3. **Plan:** მიუთითე ზუსტი ფაილი და მეთოდი, რისკი, ტესტი.
4. **Implement:** შეცვალე არსებული ფაილი, სადაც ეს შესაძლებელია; შეინარჩუნე არქიტექტურა.
5. **Verify:** გაუშვი არსებული ავტომატური ტესტები და შესაბამისი GUI შემოწმება.
6. **Document:** განაახლე დაზიანებული დოკუმენტაცია და საჭიროებისას CHANGELOG.
7. **Review:** მნიშვნელოვანი ცვლილება შემოწმდეს Pull Request-ში.

## დოკუმენტაციის წესი

- შესრულების დოკუმენტაცია იწყება `main.py`-დან, შემდეგ აღწერს `Trainer → logic → ui → exercises → data/resources`.
- მოდულის/კლასის აღწერა: `Does / Does not / Inputs / Outputs`.
- ალგორითმის აღწერა: `Goal → Inputs → Steps → Output → Educational rationale`.
- გამიჯნე `Implemented / Specified / Inconsistent / Needs Review`.
- არ წარმოაჩინო სასწავლო მაგალითი მიმდინარე სამუშაო კოდად.
- ცნობილი შეზღუდვები, კომპრომისები და გადაუმოწმებელი საკითხები არ დამალო.

## კოდის სტილი და კონტროლი

- Python: PEP 8, საჭირო docstring-ები PEP 257-ის სულისკვეთებით, საგანმანათლებლო კომენტარები რთულ ადგილებში.
- ტესტირება: `python -m pytest -q`.
- სტატიკური ანალიზი: `ruff check .`.
- სინტაქსი: `python -m compileall -q main.py trainer.py logic ui exercises`.

`pytest` და `ruff` განვითარების ინსტრუმენტებია, `tkinter` — პროგრამის GUI დამოკიდებულება. Nix-ის საბაზისო `flake.nix` ამჟამად მხოლოდ Python/Tkinter გარემოს აყენებს; ტესტირების ინსტრუმენტები შეიძლება დაემატოს ცალკე, დაფიქსირებული ცვლილებით.

## ცვლილებების ისტორია

`CHANGELOG.md`-ში არსებითი საჯარო ცვლილებისთვის გამოიყენე `Added, Changed, Fixed, Removed` და საჭიროებისას `Internal`. ისტორიული ვერსიები არ გადაწერო უხმოდ.

## უსაფრთხოება

არ ჩასვა ტოკენები ან პაროლები რეპოზიტორიაში. არ შეცვალო წვდომები, პედაგოგიური ზღვრები, `main` ან ავტომატიზაციების გაშვება ადამიანის დამტკიცების გარეშე. რეორგანიზაციის სამუშაო შტოა `chore/project-foundation`.

## Known limitations

GUI არ იფარება სრულად `pytest`-ის საწყისი ტესტებით. CI მწვანე სტატუსი არ ნიშნავს, რომ ადაპტიური Quality Gate მოქმედია ან Kiosk ყველა ოპერაციულ სისტემაზე იდენტურია.
